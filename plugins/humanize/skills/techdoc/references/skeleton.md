# 资深工程师怎么写技术方案：叙事骨架（产物序 φ）

这不是"按此顺序写"的流程，是**成品必须呈现的顺序**（skillwise 第 5 格：产物序），`scripts/verify_techdoc.py`
在出口检查它。来源：Google design doc（Ubl）、Oxide RFD 1、Amazon 6-pager / PR-FAQ、Nygard ADR、Shape Up pitch、
HashiCorp / Rust RFC、PEP 1、阿里云技术方案模板，以及 Larson / Slatton / Spolsky / Graham 的写作建议。
全部出处见 `../../humanize/references/sources.md`。

## 十个动作（proposal / design 体裁的完整形态）

| # | 动作 | 长什么样 | 来源 | AI 默认会怎么写 |
|---|---|---|---|---|
| 1 | **触发事件 + 具体痛点**，一段 | "8 月 27 日 SendGrid 503 了 20 分钟，checkout 延迟从 300ms 到 4s，估计丢了 1,100 单。" 说明为什么是现在 | Shape Up："最好的问题定义是一个具体的故事"；Bezos；Larson："从问题开始" | "随着业务的快速发展…" |
| 2 | **决定，一句话，主动语态** | "我们把通知调用改成经 SQS 异步。" 附预算 / 胃口（"两天、一个人"），是约束不是估算 | Nygard："We will…"；Shape Up appetite | 结论埋在最后一节 |
| 3 | **目标与非目标** | 唯一该用 bullet 的地方。非目标是"读者会合理以为你要做、而你明确不做"的事 | Ubl；Spolsky nongoals；Amazon 的 Goals/Tenets 例外 | 范围无限扩张 |
| 4 | **给新人的背景**，两段 + 链接 | 一个两年后接手的人只读这节能拿到全部上下文 | HashiCorp newcomer test | 行业背景 |
| 5 | **设计：先全貌后细节，只写影响取舍的部分** | 一张系统上下文图；一个有名有姓有真实数值的走查场景；角落 case 用例子拆；不贴代码 | Ubl；Rust guide/reference 分层；Spolsky 场景 | 贴代码、贴完整 schema |
| 6 | **为什么是它，而不是那两个明显的替代** | 每个替代一段，死于一个**具体的、带数字的**原因。被放弃的想法留在文档里防止再被提。再加一段诚实的"为什么不该做" | Rust drawbacks / alternatives；PEP Rejected Ideas；HashiCorp Abandoned Ideas | 4-5 个方案"各有优劣" |
| 7 | **后果，全部** | 负面和中性的也列。每个风险有触发条件、负责人、兜底。提前点名"兔子洞" | Nygard："不只是正面的"；Shape Up rabbit holes | "风险：性能、安全、推广" |
| 8 | **灰度、回滚、监控** | 灰度比例、告警阈值、回滚触发条件 | Uber 模板；阿里"安全生产" | 一行"分阶段推广" |
| 9 | **未决问题 + 尝试性答案**，以及什么证据会推翻这个决定 | "顺序：标准 SQS 不保序…我认为没事因为模板独立；产品不同意就换 FIFO，上限 300/s，我们峰值 40/s" | RFC 3 / Oxide："问题可以没有答案"；PEP Open Issues | 不存在这节 |
| 10 | **附录**：计算、压测、长讨论 | 正文引用，细节下沉 | Slatton；Collison 脚注 | 塞进正文 |

**标题**是决定本身的名词短语（"用 Redis Cluster 存 session"），不是话题（"缓存策略概述"）。
**抬头**：一个作者（不是委员会）、状态、审批人、评审截止日。

## 体裁变体（哪些动作必有）

| 体裁 | 必有动作 | 可省 | 备注 |
|---|---|---|---|
| proposal（技术方案） | 1 2 3 6 7 8 9 | 4 10 | 中文语境 8 是硬要求（安全生产） |
| design（设计文档） | 1 2 3 4 5 6 7 9 | 8 10 | 5 要有场景走查 |
| adr | 1(context) 2(decision) 7(consequences) 6(alternatives) | 其余 | 一到两页；"像和未来开发者的对话" |
| postmortem（复盘） | 时间线（1 的展开）、根因（不是"人为失误"）、为什么防线没拦住、行动项各有 owner 与日期 | 2 3 5 | 结尾是行动项不是反思 |
| memo（决策备忘 / 6-pager） | 1 2 6 7 9，全散文 | 3 以外禁 bullet | 句子 < 30 词；形容词换数据；禁 weasel 副词 |
| readme 叙述段 | 这是什么、为什么存在、不是什么、最小可用例子 | 其余 | 参考部分用表 |

## 语气规则（对所有体裁）

- 整句、成段；一段一个想法；每段能用一句话概括。
- 句子 < 30 词 / 50 字；形容词换成数字或删掉；不用 weasel 副词（"显著""基本上""nearly""significantly"）。
- "我们会…"，不是"建议采取…"；有立场，且立场后面跟理由。
- 读者从不感到意外：每个反对意见在读者想到之前已被回答（Slatton）。
- 不确定的地方**说一次、说准、放在它所在的位置**，不是全篇均匀对冲。
- 不叙述文档自身（"本节将介绍…"），不写总结段。
- 读出声来，把不像说话的地方改掉（Graham）。
- 写给两年后接手的新人和今天来挑刺的评审，不是写给审批人。
- 中文：结论先行；数字代替形容词；每张对比表以推荐收尾；不用"旨在 / 鉴于 / 值得注意的是"；不三段排比。

## AI 默认动作 → 资深工程师的动作（自检表）

| # | AI 默认 | 资深工程师 |
|---|---|---|
| 1 | "随着业务快速发展 / In today's fast-paced world" | 触发这份文档的事故、日期和数字 |
| 2 | 标题是话题（"缓存策略概述"） | 标题是决定（"订单查询加一层 Caffeine 本地缓存"） |
| 3 | 推荐埋在结论 | 第二句"我们会…"，然后论证 |
| 4 | 4-5 个方案各列优劣 | 推荐一个；每个替代死于一个具体带数字的原因 |
| 5 | "健壮、可扩展、高效" | "3 节点 10k rps P99 < 40ms；14k 时倒" |
| 6 | 处处 bullet | 处处段落，只有目标 / 非目标用 bullet |
| 7 | 均匀对冲（"可能""在某些情况下"） | 有证据处直说；一两个真未知明说并给出消除方法 |
| 8 | 只列收益 | 后果节列代价，再加一段"为什么不该做" |
| 9 | 范围覆盖一切相邻事物 | 非目标点名"读者会以为你要做但你不做"的事 |
| 10 | "风险：性能、安全、推广" | 每个风险：触发条件、负责人、兜底 |
| 11 | "本节将讨论…" | 直接说；标题承担结构 |
| 12 | 每节小结、全文"综上所述" | 点到即止；结尾是未决问题和下一步 |
| 13 | "用户提交请求" | "梅，Shopify 商家，4 万 SKU，每天 09:00 批量上传" |
| 14 | 先抽象定义，例子也许后面有 | 先例子，后抽象 |
| 15 | 同样句长 + 首先 / 其次 / 此外 | 长短交错，一句长的后面跟一句短的 |
| 16 | "不是 X 而是 Y"、三连并列 | 一句一个主张；两个够就两个 |
| 17 | 被否决的方案悄悄删掉 | 留下并写原因，防止再被提起 |
| 18 | 替代方案从原则上论证 | 从先例和数字论证（"LISTEN/NOTIFY 压测 8k 订阅就顶了"） |
| 19 | 上线是最后一行 | 灰度比例、告警阈值、回滚触发条件 |
| 20 | 贴代码、贴完整 API schema | 只画决定取舍的那部分接口；代码进附录或不出现 |
| 21 | 每句一个"以实现… / 以确保…" | 目的在目标节说一次；句子说发生什么 |
| 22 | 权威、定稿的口气 | 标为讨论稿；"及时胜于打磨"；向评审提具体问题 |
| 23 | 写给审批人看一遍 | 写给两年后的新人和今天的怀疑者 |

## 一个反例剖析（`../../humanize/fixtures/ai-zh.md` → `human-zh.md`）

AI 版 695 字：背景段零事实 → 四条加粗目标 → 首先 / 其次 / 最后 的架构 → 四条"关键技术点" → "可能面临一定风险" → 综上所述 + 让我们共同努力。
humanlint 65/100，cold-reader 在第 1 段就 `lost_at`（"值得注意的是，缓存作为…"），全文 0 个数字。

人写版 624 字：上周三 P99 80ms → 1.4s，DB 连接池打满两次 → 92% 读请求集中在 5% 订单 → "我建议给这一个接口加缓存"
→ 目标一句话（P99 150ms、DB 读砍半）→ 怎么做（Caffeine 5 万条 60 秒、删 key 不用 MQ）→ 没选只用 Redis（2ms 往返）、
没选 write-through（改动面三倍）→ 最担心的两件事各有兜底 → 排期 + 回滚 → 一个没想清楚的点（客服后台改单）。
humanlint 2/100，14 个数字，1 个立场标记，0 个路标词。字数更少，信息多一个量级。
