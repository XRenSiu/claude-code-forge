# PSL 推导示例

两个例子。例 1 是完整推导（需求 → 朴素实现为什么错 → 提问轨迹 → 带原子标注的完整 PSL）；
例 2 是不同领域的迷你例，证明模式可复用。**对照的是形状，不是内容**——这里的世界属于这两个
虚构产品，别抄进别的产品。

标注约定：`[Σ]` 世界事实（描述"是什么"）；`[φ]` 判据（裁决"什么算对"）；`[γ]` 过程约束
（管住"何时停、何处留给人"）。

> 注意：本文件是示例讲解，**不是一份 PSL**——直接对本文件跑 `verify_psl.py` 会得到假失败。
> 要试跑预门，把例 1 围栏内的 PSL 抽成独立文件再跑。

## 例 1 · 记忆产品的"按时间搜索"（完整推导）

### 原始需求

> 让用户能按时间搜索记忆。

### 朴素实现为什么错

照字面读：`memories` 表 + `created_at` 字段 + 日期范围选择器。一个日历筛选器。
**技术上完全正确**——这正是它危险的地方。

产品上错在哪：用户说"上个月"时偶尔确实指日历；但说"在东京的那段时间""刚分手那阵子"
"大学那会儿"时，指向的是**一段有边界、有主题的生活时期**。人类的自传体记忆按时期
（lifetime periods）和事件（general events）组织，不按时间戳组织——这是心理学通识，
引擎知道，但照字面实现时**不会主动说**。`{created_at}` 的世界里没有任何实体能承载
"那阵子"，于是"按时间搜索"被静默降维成"按日期过滤"。

症状签名：需求里的领域词（"时间"）被直译成数据类型（timestamp）。这就是"用默认值把
世界填错"。

### 提问轨迹（交互的形状）

**Surface（自己填，不问，展示给用户确认）**：

> 我先填了我能确定的通用世界事实，请扫一眼有没有错：
> - 人类回忆按"时期/事件"组织，不按时间戳（心理学通识）；
> - "上个月"这类词在记忆语境里有日历/时期两种读法，歧义真实存在。

**Elicit（私有且承重，一次一个主题，带推荐答案）**：

> **问 1（核心赌注 · 决定 Vision）** 这个产品赌的是什么？
> A) 记忆的价值在被重新**找到**——搜索是检索工具，求准求快
> B) 记忆的价值在被重新**体验**——搜索是回到那段时间的入口
> C) 记忆的价值在被整理成**叙事**——搜索服务于人生编辑
> 推荐 **B**：与"按时间"这个入口词最一致（按时间回去，不是按关键词命中）。回 1A/1B/1C 即可。

> **问 2（时间心智承诺 · 决定 Mental Model 与消歧默认）** 用户说"去年夏天"而系统拿不准时：
> A) 默认按日历（2025-06 ~ 2025-08）
> B) 默认按时期（命中"毕业旅行"那段）
> C) 双解并示，请用户选
> 推荐 **C**：歧义是这个领域的真实属性，替用户猜等于把世界私自填掉。

**Seam（问了答不上来 → 不纠缠，进 Open Questions）**：

> **问 3（目标 Persona）** 主用户是记录密度高的日记型用户，还是偶尔翻旧照的轻量用户？
> 用户答："不知道，先写吧。" → 该槽标为 Open Question，写清它为什么承重，**不用默认值糊**。

### 产出的 PSL

```markdown
# PSL-记忆时间搜索

## Vision（愿景）[Σ]

这个产品赌：**记忆的价值在于被重新体验，而不是被检索命中。**
"按时间搜索"是回到那段时间的入口，不是查询日志的工具。
（此命题推翻朴素实现：若只求检索命中，日历筛选器就够了。）

## Mental Model（心智模型）[Σ]

- **时间不是时间戳。** 用户的过去按"时期"（Era）与"锚点事件"（Anchor）组织；
  时间戳只是其中一种坐标。
- 一段记忆同时活在两套坐标里：**日历时间**（2025-03-12）与**叙事时间**（"在东京的
  那段时间"）。
- 时期的边界由情感锚点划定（搬家、分手、换工作），不由日期划定；边界是模糊的、可重叠的。
- "上个月/去年夏天"这类词天然歧义（日历读法 vs 时期读法），歧义属于世界本身，不是解析失败。

## Domain Model（领域模型）[Σ]

| 实体 | 是什么 | 朴素实现里有吗 |
|---|---|---|
| Memory | 一条记忆（内容 + 双坐标） | 有（但只有单坐标） |
| **Era（时期）** | 用户生活的一个命名阶段；边界模糊、可重叠；有主题 | **没有** |
| **Anchor（锚点）** | 划分时期的标志性事件（搬家、分手、入职） | **没有** |
| **TimeReference（时间指称）** | 查询中的时间表达；解析结果 ∈ {日历区间, Era, Anchor 邻域} | **没有** |

关联：Memory ∈ 0..n 个 Era（重叠合法）；Era 由 1..n 个 Anchor 划界；
TimeReference 消歧后指向三种坐标之一。

（Domain Model 推翻测试：照此建库得到 Era / Anchor / TimeReference 表；照字面需求建库
只得到 `{memory, created_at}` 单表。两者不同 → 这份 PSL 干活了。）

## State Machine（状态流转）[Σ]

领域动力学，不是执行顺序：

- **Era**：潜在（系统从记忆聚类中察觉到一段疑似时期）→ 成形（有锚点 + 主题）→
  已命名（用户确认并命名后才可用于消歧）→ 归档（用户标记结束）。
- **TimeReference**：未消歧 → 已消歧（日历 | Era | Anchor 邻域）| 双解待选（歧义时）。

## Workflow（工作流）[Σ+φ]

**Σ · 用户按时间搜索时，世界里发生了什么**：一次"指称消歧"——查询中的 TimeReference
被解析到三种坐标之一，依据是指称的词汇形态、用户的历史偏好、以及当前 Era 库存；随后
以命中的坐标重建"那段时间"。

**φ · 消歧判据**：

- 精确日期形态（"3月12日""上周二"）→ 日历坐标；
- 叙事词形态（"大学那会儿""在东京的时候"）→ Era 坐标；
- 情感锚形态（"刚分手那阵子"）→ Anchor 邻域；
- 真歧义（"去年夏天"）→ 双解并示，请用户选，**不替用户猜**（问 2 的用户承诺）。

**φ · "对"的结果长什么样**：返回的不是命中列表，而是"那段时间"的重建——核心记忆 +
时期上下文（Era 名、边界锚点、主题）。一个平铺的、无上下文的结果列表即使召回全对也算错。

## Acceptance（验收）[φ-出口]

- 问"我在东京的那段时间" → 返回 Era=「东京时期」的记忆簇，携带时期摘要（Era 名 +
  边界锚点），而非按 created_at 过滤的平铺列表。
- 问"3月12日" → 返回该日历日的记忆（精确形态走日历坐标，不强行套时期）。
- 问"去年夏天"（歧义）→ 返回双解（日历：2025-06~08 / Era：「毕业旅行」）并请用户选，
  不擅自二选一。
- 问一个没有任何 Era 覆盖的时段 → 返回日历结果 + 提示"可以为这段时间命名一个时期"
  （优雅降级，不报错、不假装有时期）。
- 问"刚分手那阵子" → 返回以该 Anchor 为中心的邻域记忆，跨越日历上不连续的日期也合法。
- 照本 PSL 建库 → schema 含 Era / Anchor / TimeReference 实体（与照字面需求建出的
  `{memory, created_at}` 单表不同——朴素实现被推翻的物证）。

## Personas / Jobs [Σ·用户]

意图词表（场景 → 元素映射）：

- "那阵子 / 那会儿 / 那段时间 / 当时" → Era 坐标；
- "X月X日 / 上周 / 2024年" → 日历坐标；
- "刚 X 的时候"（X 为情感事件）→ Anchor 邻域。

（主 Persona 未定，见 Open Questions——意图词表先按两类用户的并集写，收窄待人定。）

## UI Contract [φ]

产物须呈现的性质（出口可检，不是交互流程）：

- 时间搜索的结果页必呈现时期上下文（Era 名 + 边界锚点），不得只给列表；
- 歧义指称必呈现双解选择控件；
- 无 Era 覆盖的时段，结果页必含"为这段时间命名"入口。

## Design Principles [φ]

- **叙事完整性 > 检索精确率**：两难时，宁可多带出一个时期的完整上下文，不追求最小命中集。
  （能裁决冲突：某优化提高精确率但会剥离时期上下文 → 按此原则否决。）

## γ 约束

- done_when：TimeReference 的三坐标消歧规则全部落地，且六条验收全部可跑。
- **未经用户确认的 Era 不得用于消歧**（潜在/成形状态的聚类结果只能作为建议呈现）——
  防止系统的私有世界覆盖用户的世界。机器可判到此为止；"这个 Era 划得对不对"是留给
  用户的残差。

## Open Questions（seam）[γ→人]

- **主 Persona 未定**（用户答"不知道"）：日记型重度用户与轻量翻旧照用户，对 Era 密度与
  消歧默认的要求不同——这会改变意图词表的收窄方向与冷启动策略，需产品负责人裁决。
- **冷启动**：新用户零 Era 库存时，"按时间搜索"的第一周形态（纯日历 + 引导建 Era？）——
  取值翻转"无 Era 覆盖时段"那条验收的具体形状，物料与访谈中无此数据，需人定。
```

### 复盘：这份 PSL 推翻了朴素实现的什么

| 维度 | 朴素实现 | 照 PSL 推导 |
|---|---|---|
| Schema | `{memory, created_at}` 单表 | + Era / Anchor / TimeReference |
| 查询语义 | 日期范围过滤 | 三坐标指称消歧 |
| 结果形态 | 平铺列表 | "那段时间"的重建（记忆 + 时期上下文） |
| 歧义处理 | 不存在歧义概念 | 双解并示，用户裁决 |

## 例 2 · 迷你例：协作工具的"已读"（不同领域，证明模式可复用）

**需求**：给团队协作工具的任务加"已读"功能。

**朴素实现为什么错**：`read_receipts` 表 + boolean。但在协作语境里，"看过"承载的是
**社会信号**：发起人真正想知道的常常不是"你的视网膜扫过了"，而是"你接了这件事吗"。
把两者压成一个 boolean，会造出"已读=已接手"的误会机器（已读不回的社交压力即由此来）。

**PSL 骨架**（只示形状）：

- **Vision** `[Σ]`：赌"已读"的价值在消除协作中的责任模糊，不在阅读监控。
- **Mental Model** `[Σ]`：看见 ≠ 接手；"已读"在团队语境里被读作承诺信号，且不同团队
  约定强度不同。
- **Domain Model** `[Σ]`：拆出两个实体——View（注意力事实：谁的视线经过）与
  **Acknowledgement（承诺事实：谁明确接了）**。朴素 boolean 表里没有后者 → 推翻测试过。
- **State Machine** `[Σ]`：任务对每个成员：未触达 → 已见（View）→ 已应答
  （Acknowledged / Declined）。"已见"不会自动流向"已应答"——那条边只能由显式动作触发。
- **Workflow** `[Σ+φ]`：Σ——成员打开任务时产生 View 事实；点"收到/接了"时产生
  Acknowledgement。φ——发起人视图里两类事实**必须可区分**；View 不得被渲染成任何
  带承诺语义的文案（"已读"这个词本身要小心）。
- **Acceptance** `[φ-出口]`：问"谁看过这个任务" → 返回 View 列表；问"谁接了" → 返回
  Acknowledgement 列表；一个只 View 未 Ack 的成员 → 在发起人视图中显示为"已见·未应答"，
  而非"已读"。
- **Open Questions** `[γ→人]`：View 事实对全员可见还是仅发起人可见？——隐私文化承重
  （监控感 vs 透明感会改变产品性格），团队未表态，seam 留给人。

## 用法提醒

写 PSL 时对照这两个例子检查三件事：Domain Model 有没有推翻测试的**物证**（表格里那列
"朴素实现里有吗"）；Acceptance 是不是全部"问 X → 返回 Y"；Open Questions 里每条有没有
写清**为什么需要人来定**。
