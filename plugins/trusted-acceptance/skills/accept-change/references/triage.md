# 结果分流与预算

| 状态 | 行动 | 不应做什么 |
|---|---|---|
| queued / running | 保留 run_id，在剩余时间内间隔查询 | 每次轮询新建请求或清零预算 |
| accepted_for_stage | 转述该 binding 与阶段的控制入口结论 | 自动等同于可合并/可发布 |
| needs_repair | 输出预期、实际、fixture、复现步骤与证据，交项目 Harness 修复后提交新候选 | 在验收中修代码、删断言或只报“质量不够” |
| infrastructure_blocked | 按批准配方和环境恢复预算处理 | 无依据让产品实现返工 |
| checker_blocked | 提出检查器修补，回归后批准新包再验 | 原地改预期、test.fixme 或把异常当通过 |
| needs_review | 保留完整历史，解释同条件波动/未解决发现，交受控复核 | 无限重跑直到出现绿色 |
| obsolete | 归档迟到结果，读取当前任务 | 推进取消任务或旧候选 |
| blocked | 明确歧义、缺能力、漏项、未知、证据/身份/授权缺口 | 以总分、模型共识或自报 passed 替代 |

本地核心的 `eligible` 只表示输入在程序规则下自洽，报告必须写“本地非正式建议”；它不是远端 `accepted_for_stage`。

实现失败反例应具体，例如：“候选 C17，fixture doc-17，所有者收到关闭成功后，匿名 GET 仍返回正文；预期拒绝，见 E42。”有复现证据才判断可通过实现返工解决；环境、权限、需求和观察能力缺口走各自路径。

累计预算按任务持久化，包括代码返工次数、环境恢复次数、截止时间与费用。建议初始值为 2 轮代码返工、1 次环境恢复；这只是配置起点。请求不能指定提高预算，进程/会话/候选变化不重置任务计数。控制区在分配新尝试前预留预算，完成后记实际消耗。超时后不自动提交新的有副作用任务。

幂等键对同一请求保持稳定；同键不同内容服务端拒绝。网络超时可能已经成功创建运行，保留原请求再查/重试；不生成新键“解决”超时。每个新结果文件用新名字，旧文件保留。客户端不会自动重试或无限轮询。

生产调度需持久队列、租约与 fencing token，避免重复 worker 的迟到结果改当前状态。验收和交付状态分别管理；当前有效授权和取消状态须在结果发布与实际交付前原子复核。

形式化证据的分流见 [formal-evidence.md](formal-evidence.md#分流)：只有在真实代码里重放成功的反例才是实现缺陷，只在模型里出现的反例按模型失真处理，规则缺口走产品裁决。
