# 推导对应：PSL 六层 → 三样产物

| PSL 层 | 喂给 | 推什么 |
|---|---|---|
| Vision | 形态草案的"明确不做" | 根命题否定掉的形态 |
| Mental Model | Workflow φ、形态草案的交互 | 用户以为世界怎么运转 → 界面必须顺着它 |
| Domain Model | DOS 提案 objects / relationships | 应然本体；对象 ≤ 7；不造 PSL 没有的实体 |
| State Machine | DOS 提案 behaviors、Workflow Σ | 状态流转 → 副作用清单 |
| Workflow（Σ+φ） | workflow.md | 原样投影，禁步骤化 |
| Acceptance | 形态草案的验收挂钩 | 每条形态决策至少能被一条 Acceptance 检到（否则它是装饰） |
| Personas / JTBD | 形态草案界面层 | 意图词表 → 元素映射 |
| UI Contract / Design Principles | 形态草案 | 产物须呈现的性质、冲突取舍 |

引用锚有四种：`PSL-NNN`（规律索引）与 `UI-n` / `A-n` / `DP-n`。UI Contract / Acceptance /
Design Principles 三层同样承重——决策真正推自 UI-1 时就引 UI-1，别借最近的规律再补一句
`(via UI-1)`：借来的引用让 G1 的"推错了 vs 规律错了"失去着力点（dogfood 2026-09-05，I-19）。
规律标了 `（内容层）` 的约束的是产物内容，不该出现在形态草案里（I-20）。

## 引用数据文件结构的决策：必须带该文件的一行证据

一条形态决策若断言某个数据文件长什么样（`graph.yaml` 的节点与边、`dos.yaml` 的键、某 schema 的
顶层结构），它必须在决策里带上那份文件的**行级证据**（`graph.yaml L320–321`）。

理由是一次真实的踩坑：本次推导把"同阶段"定义成"同一 stage 节点出发的 conditional 边"，听起来
像在描述数据，实际与 `graph.yaml` 不符——实现侧的两条 conditional 边从 skill 节点出发，契约侧
两个 handler 之间根本没有 conditional 边。按字面执行会豁免掉零个本该豁免的分支。G1 对着原始数据
才发现（I-36）。

这类错误的特征是**读起来完全合理**：它用了数据文件里真实存在的词，只是把结构记错了。防它只有一招
——写决策时打开那份文件，把行号抄进来。`verify_derived.py` 对"提到数据文件结构却没有定位符"的
决策给 flag；flag 不是判决，是提醒你去核对那一行。

## 含谓词的决策：至少走查一个最小样例

决策里出现"当且仅当 / ∧ / 缺一不算 / exit 0 / 若…则"这类可计算条件时，同一行里给一个走查例：
`例：<最小输入> → <判定>`。

理由同样来自实测：形态草案的三处谓词（双生产者、orphan-gap、未行使的人签门）都是在 L5 作者把它们
编进 fixture 时才发现欠定的，其中一处测试选错了读法，等发现时测试已经上锁，只能走变更提案（I-56 /
I-58）。谓词能不能对一份最小样例算出来，是 G1 的第四问——不是写测试时才该问的。

同理，「实体与数据形态」里每种记录类型都要写落位：落在产物的哪个顶层键、被谁以什么字段引用。

## 分歧集的比对方法

1. 把每个版本的形态草案按 `[F-nn]` 决策点对齐（同一决策点可能编号不同，按语义对齐，记录映射）。
2. 逐点比较：选择相同且引用相同 → 一致；选择相同引用不同 → 一致但记"多源"；选择不同 → 分歧。
3. 分歧率 > 50% → 不合并，回报"PSL 约束太弱"。
4. 每条分歧写议程：是 PSL 某条规律含糊（改 PSL）、是承重槽没填（补 Mental Model / Open Question 请人定）、
   还是推导者即兴（舍弃）。

## "技术对、产品错"的信号

- 形态草案里出现 PSL 没有的实体名（`TimeBucket`、`Filter`）。
- 决策引用的是 Domain Model 之外的常识（"用户通常想按日期筛"）。
- Workflow 写成了执行顺序。
- 验收挂钩缺失：某条形态决策没有任何 Acceptance 能检到。
- 三个版本在同一决策点上给出三种界面——这个点在 PSL 里是空的。
