# 双轨判据：PSL 轨 vs TASK 轨

## 一句话

**语义份额 × 变化率高、实现原语难度低 → PSL 轨；确定性主导 → TASK 轨。**

## 速判（三问，任一"会"即 PSL）

1. 把需求交给一个**不了解这个产品**的工程师照字面做，他会不会交出"技术正确、产品错误"的东西？
   （典型：按时间搜索记忆 → 日历筛选器。）
2. 需求里的关键词（"相关""合适""自然""智能理解"）能不能被现有 DOS 的属性解析？不能 → 世界没建。
3. 验收能不能不靠人"看一眼"就判？全靠看 → 先建世界再定判据。

## 客观触发（脚本判，不靠自评）

`verify_issue.py --dos dos.yaml`：`Depends on DOS` 里的 objects / invariants 有任何一个不在 dos.yaml
里 → 输出 `force_track: psl` 与缺失词表。自信而错的人会绕开 G1，闭包检查不会。

## 混合需求

只对体验性内核走 PSL；确定性部分注明"留在 TASK 轨，按字面做"。一条 issue 可以两段范围：
`scope.do` 标注 `[psl]` / `[task]`。

## PSL 轨的 issue 什么时候建

在 G1 之后。issue 的 Intent 引用签字版形态草案的 sha256 与 `g1-record.md` 路径；范围段来自功能级
PSL 的范围段。没有 G1 记录 → 不建，先 `/psl`。

## 反例（不要过填）

支付校验、合规字段、固定列的报表导出、CSV 六列——PRD 的精确恰好够用，套世界模型是过填。
