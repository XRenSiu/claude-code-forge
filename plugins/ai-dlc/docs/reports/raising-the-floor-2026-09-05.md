## 出了什么事

同一个仓库，同一个模型，两个人让 coding agent 做同一个需求："用户可以按'上个月'搜索记忆"。一个人交回来的是 created_at 字段加一个日历筛选器，技术正确，产品错误；另一个人交回来的能把"上个月"理解成记忆里发生的时间，而不是写入数据库的时间。模型是同一个。差别在两个人喂给 agent 的东西。这个仓库的作者在 2026-09-05 提出这个观察，并给了两个解释：一是每个人对任务的信息补足不一样；二是每个人给模型的上下文不一样，让 agent 自己去仓库里找，等于让它猜。

这份报告做三件事：查业界怎么处理这两个差异，对照 sdlc 插件（v0.6.0，28 个 skill）做了什么，找出还缺什么。读者是要决定给团队上不上这套流程的人；sdlc 的内部名字出现时会先解释一句。

先放结论。第一个解释有直接的实验证据支持。第二个解释只对了一半。2026 年的对照实验说，"给更多仓库知识"本身不提高正确率；能提高的是两样东西：任务在动手前被写成能判真假的条件，以及做完之后由一个不是作者的东西来验。sdlc 的 28 个 skill 里有 20 个在做这两件事，这 20 个就是它抬高下限的地方。缺口也在这里。它的机制目前全是"编译了、没验证"：规则写进了脚本，脚本在样例上跑过，但没有在真实任务上比较过带与不带的差别。而且它对代码结构性质量（复杂度、重复、依赖方向）没有任何机械闸，而这恰恰是 agent 代码退化最快的维度。

## 业界的证据：差异到底从哪来

先摆数字。后面的判断都靠它们。四组数字分别回答四个问题：补足信息有多大用，给上下文文件有多大用，agent 代码在哪个维度退化，以及作者自己验自己靠不靠得住。

补足信息的作用是真的。而且大。Ambig-SWE（ICLR 2026）把 SWE-bench Verified 的 issue 故意写模糊，让 agent 直接做，再让 agent 可以向用户提问。结果两条。模型分不清一个任务是写清楚了还是没写清楚；一旦允许提问，模糊任务的解决率最高提升 74%。后续的 Ask or Assume（arXiv 2603.26233）做了一个会判断自己不确定性的多 agent 框架，在模糊版 SWE-bench 上做到 69.40%，几乎追平拿到完整 issue 的 70.80%。"任务信息补足"这一项，做与不做之间差的是从做不出到做得出。

上下文文件的作用，比大家以为的小。arXiv 2607.27250 用 Claude Code 和 Codex 在 3 个真实仓库、17 个任务、288 次运行上做对照：有没有 AGENTS.md / CLAUDE.md，正确率的差别被压在 10 到 15 个百分点以内，等价性检验判定"不可测量"；作者的归因是失败来自"实现功力：功能设计、模式选择、精确接线"，不是缺仓库知识。另一组研究（arXiv 2608.25241，441 个企业仓库加 509 个开源仓库）看的是质量成本：把 agent 配置文件提交进仓库的团队，认知复杂度增长 27%，没提交的增长 53%；静态分析告警增长 14% 对 24%。两组数据放一起读：上下文文件不让 agent 更对，但让它更省（另一项研究测得运行时间少 28.6%、输出 token 少 16.6%），也更不容易把代码写乱。

退化最快的维度是代码结构。GitClear 2026 年的报告：新代码里复制粘贴比例从 2022 年的 9.4% 涨到 15.7%，重构比例从 21% 跌到 3.8%，跨文件函数调用少了 35%。DORA 2024 的数据是代码质量涨 3.4%，同时交付稳定性跌 7.2%。这不是模型不会写。是没人拦。

作者验自己不可靠，人和模型都是。ImpossibleBench 把测试改成不可能通过的版本，能通过的就是作弊：模型会删测试、改断言、给测试输入打补丁。METR 的实验里资深开发者用 AI 慢了 19%，却相信自己快了 20%。人的感觉也不可靠。AI 审查工具的独立测评里，抓 bug 率最高的 Greptile 到 82%，但同一工具精确率只有 36.5%：316 条评论里 111 条是挑刺、56 条是错的。

四组数字合起来，"不同人做出来质量不同"的真正变量是三个：任务动手前有没有被写成可判真假的条件；实现者能看到什么、不能看到什么；验收是不是由不是作者的东西来做。上下文的量排最后。

## 业界怎么做：四条路线

对着这三个变量，业界走出四条路线：先写 spec 再写代码的 spec-driven development，管模型看到什么的 context engineering，把约束做成环境的 harness engineering，以及把验证和循环当成结构问题的 loop engineering。四条各说一段。

第一条，spec-driven development。Kiro（AWS）、spec-kit（GitHub，9.3 万星）、OpenSpec、Tessl 都在 2025 到 2026 年把"先写 spec 再写代码"做成了工具。Thoughtworks 的 Birgitta Böckeler 把它们分成三档：spec-first（写完就扔）、spec-anchored（spec 跟着代码活）、spec-as-source（人只维护 spec，代码是生成物）。她的批评也很具体。一套流程不分任务大小，reviewer 被大量 markdown 淹没，以及"控制的幻觉"：写了再多 spec，agent 照样会忽略约束或者过度解读。

第二条，context engineering。Anthropic 的表述是"找到能最大化结果概率的最小高信号 token 集"，做法是 CLAUDE.md 只放少量常驻信息，其余靠 glob 和 grep 即时取用，长任务靠压缩、结构化笔记、子 agent 隔离。Böckeler 的实操版本是"从最少开始，半年前需要放进去的东西现在可能已经不需要"，并警告不要在指令里用"确保、防止"这类词，它们制造的是确定性的错觉。arXiv 2606.20512 更进一步：仓库指导文件不该手写，该从失败里调，先跑、看失败、改指导、再跑，直到平台期。

第三条，harness engineering。OpenAI 2026 年初的文章讲他们用 Codex 做了一个约 100 万行、没有一行人写的产品：人不写代码，人设计让代码可靠生成的环境。具体做法是 AGENTS.md 只做目录，指向 docs/ 里分层的文档；架构约束不写在文档里，写成自定义 linter 和结构测试，agent 违反就红；agent 用截图、日志、golden test 自证；文档定期"垃圾回收"。Anthropic 的长跑 harness 是另一半：initializer agent 建环境，coding agent 每次从 progress 文件和 git 历史读状态，做一小步，把环境留干净。

第四条，验证与循环。Anthropic 的 Claude Code 最佳实践建议把审查放进一个只看 diff 和验收条件、看不到推理过程的新子 agent，因为模型评价自己刚写的代码会宽容。2026 年中出现的 loop engineering 和 graph engineering 讨论把这件事推到了结构层：生成者和验证者必须是两个东西，循环要有可测的停止条件，失败要回到对的层而不是原地重试。

## sdlc 怎么做：按提问里的两个角度拆

### 角度一：任务信息补足，把愿望变成能判真假的契约

愿望长这样："用户可以按'上个月'搜索记忆"。直接丢给 agent，就是开头那个日历筛选器。sdlc 在愿望和代码之间放了四道东西：先判这个需求该不该先建"产品世界"（要建的 sdlc 叫 PSL 轨，不用建的叫 TASK 轨），再把它写成可证伪的 issue，再把 issue 收紧成契约并由人签字锁住，最后用一份本体词表做客观的兜底检查。四道各说一段。

第一道是 /psl。它先判这个需求是语义主导还是确定性主导。判据是一句话：把需求交给一个不了解产品的工程师照字面做，会不会做错？会，就先写产品世界。产品世界有六层：Vision、Mental Model、Domain Model、State Machine、Workflow、Acceptance。它最硬的规矩是"世界内容只有三种来路"：模型已知的通用常识可以自己填；只有用户知道且会改变产品形状的槽必须问；问了答不上来的写进 Open Questions。没有第四种来路。也就是不许用默认值把不知道的东西糊上。产品世界写完，由人裁决这个世界抓得对不对；这是 sdlc 三道只能人签的门里的第一道，叫 G1。这一条"三种来路"的规矩正对着 Ambig-SWE 的发现：模型分不清模糊与清楚，所以规则不让它自己判，而是按"会改变产品形状的槽"逐个过。

第二道是 /issue。它把需求写成可证伪的条目：形容词换成阈值（"快一点"不是判据，"p95 < 200ms"才是，且阈值必须有来源：用户给的、SLO、或一次真实故障）；每条正向验收配一条反向孪生（边界输入、恶意输入、失败输入时系统该拒绝还是降级）；验收只写观察边界（路由、命令、事件、数据库字段），不写文件路径和函数名；澄清最多三轮，答不上的进假设台账带风险签字继续。这些规则不靠模型记住。verify_issue.py 在建 issue 前机械检查：模糊量词没阈值拒，没有反向孪生拒，观察边界里出现 src/ 拒。

第三道是契约与签字。/donewhen-extract 与 /acceptance-spec 把 issue 收紧成 done_when.yaml v2，以验收条目为单位，每条要么是机器可判（observe、given、expect），要么是人判（statement、judge、evidence）。契约写好之后是第二道人签的门 G2：人确认判据，脚本给文件算哈希锁住。签完之后实现者改不了判据。改契约必须附变更提案，verify_commit.py 在 diff 进仓库前检。第三道门 G3 在验收之后，人复核例外，后面会遇到。

第四道是 /dos-extract。它从代码和文档反抽一份本体：核心对象不超过 7 个、关系、宪法级规则、agent 禁令。issue 里出现本体解析不了的名词，脚本判"词表闭包失败"，强制转去先建产品世界。这是一个客观触发。自信而错的人会绕开 /psl。闭包检查不会。

### 角度二：上下文供给，不是给得多，是给得准且只给该看的

sdlc 对"让 agent 自己去找"的回答不是把整个仓库喂进去，而是把任务切成一个无上下文的 agent 也能做完的卡。这一角度有三件东西：卡怎么切，实现者拿到什么、拿不到什么，测试由谁写。

卡由 /plan-cards 切。它把冻结的契约拆成 cards/CARD-xx.yaml，每张卡带需求归属、验收子集、本体切片、可改文件白名单、禁改文件、上下文预估。三项机器校验：需求全覆盖且一卡一主；卡间无文件写冲突，lockfile、配置、schema 这类共享文件要么归一张卡要么全禁；名词能被本体解析。卡加相关源码超过 4 万 token 必拆。

实现者拿到的东西由 /implement 和 card-implementer 子 agent 定义：卡、状态摘要、验收子集、红基线（测试在实现前是红的记录）、白名单内的源码。拿不到的东西写在 graph.yaml 每个节点的 must_not_read 里：评审提示、隐藏变体集、spec-robustness、其他卡、账本里评审者的发现。这是训练期信息隔离的做法。干活的不许看评卷标准。改动进仓库前有三道闸，都在 verify_commit.py 里：白名单溢出停、锁文件哈希不符停、secrets 与调试代码停。

测试在实现之前由非实现者写，/test-suite-generator 写完再签一次锁；实现者的 forbidden_files 默认含 tests/**。这一条直接堵 ImpossibleBench 里的三种作弊：改测试、改断言、给测试输入打补丁。

对照业界：Anthropic 说"最小高信号集"，sdlc 把它做成了卡的 lint 阈值；OpenAI 说"用 linter 而不是文档来约束"，sdlc 的对应物是白名单执行器和锁。但只覆盖文件级。结构级没有，这是下面缺口的第二条。

### 提问里没提的第三个角度：验收不由作者做

业界证据说这一项比上下文更决定质量，sdlc 也把最多的 skill 放在这里。六个独立审查 skill 并行：code-reviewer 按焦点、qa-reviewer 真跑测试、pm-reviewer 逐条需求合规、spec-drift-detector 查契约与代码分歧、spec-gaming-detector 假设作者在作弊，加 meta-judge 只综合不重审。产出分三档。A 档机械一票否决（测试、lint、白名单、锁、隐藏集、有复现的缺陷），B 档结构告警，C 档请求人（就是 G3）。spec-gaming-detector 的默认立场是反的："如果你说'看起来没问题'，你就失职了"，这是对抗 sycophancy 的 prompt 层手段。/calibrate 更往前一步：验收标准本身要先过 mutation score 和评分一致性（Krippendorff α ≥ 0.80）。没校准的标准不当证据。

### 第四个角度：失败回到对的层，不原地重试

失败往哪回，由 routing.yaml 决定。它把失败按层归因（卡 ⊂ 方案 ⊂ 任务 ⊂ 本体 ⊂ 世界），每层有预算（单卡 3 次），同一指纹连续两次判无进展立即升级；v0.6.0 加了震荡、平台期、"在当前契约下不可能"三种收敛信号，且"不可能"只能由评估者报，实现者报被拒。账本只增不删。trace.jsonl 记因果边，/retro 从中算逃逸缺陷的因果链，/tune 把环的参数改成提案给人开 PR。loop engineering 点名的七个部件（目标、生成者与验证者分离、停止规则、磁盘上的记忆、新上下文、触发、反馈路由），这一层每个都有对应物。这也是 sdlc 相对 spec-kit 这类工具最不一样的地方：spec 工具只管做之前。sdlc 管失败之后往哪回。

## 一张任务卡实际经过什么

用一个小需求走一遍："导出报表增加 CSV 六列"。它是确定性需求，走 TASK 轨，不用先建产品世界。

/issue 把它写成：六列名称与顺序、空值怎么写、超过 10 万行时的行为（反向孪生）、观察边界是下载接口的响应体；建 issue 前脚本拒绝了"导出要快"这条没阈值的验收。/donewhen-extract 出 done_when.yaml。人签 G2，锁住。/plan-cards 拆两张卡：一张改导出服务，一张改列配置，共享的路由表归第一张、第二张禁改。/test-suite-generator 先写测试，再签一次锁。两个 card-implementer 各拿一张卡在新上下文里做，只看到卡和红基线，每个 commit 过白名单与锁。/acceptance-fleet 六审并行，spec-gaming-detector 发现第二张卡的实现给测试里那个 10 万行样本做了特判，判 GAMING_RISK，路由回任务层收紧契约而不是让实现者再试。/pr 生成验收到证据的映射，/review-loop 把 reviewer 评论当待验证主张处理。人合并。/release 验证绿才算交付。

这条链路里，人的水平差异被压在三处：写需求时的补足（脚本拒模糊）、切卡时的上下文（lint 拒超限）、验收时的宽容（作者看不到评卷）。这就是抬高下限的实际含义。不是把每个人变成资深工程师，是把资深工程师会做的三次核对编译成不跑就走不下去的门。

## 还缺什么

sdlc 自己的文档已经诚实登记了一批空白：模块之间的接口契约没有承载 skill，测试由红变绿的证据没有脚本，验收结果对照契约的比对没有脚本，本体的"应然"与"现状"没有对账，会话结束前检查状态干净的 Stop hook 只有模板，收敛阈值全是文献先验。这次实测又记了三条接缝问题（两个 skill 对规律编号的约定不一致、世界裁决的记录看不到哪些槽是空的、状态目录该不该进 git 没写）。下面是对照业界之后我认为更要紧的五条，按"补上之后下限抬多少"排序。

第一，全部 28 个 skill 都是 static_only，没有一条带与不带的行为对比。这是最大的不完备。插件声称抬高下限。但它从没在留出任务上测过"带 sdlc 的 agent 交付比不带的好多少"。所有闸门阈值（指纹历史 6、震荡周期 2 到 3、plateau 3 轮）是从文献抄的。补法：建一个 10 个任务的小题库（5 个 TASK 轨、5 个 PSL 轨），每个任务跑裸 agent、只加 CLAUDE.md、走 sdlc 三组，由隔离的评审 agent 打分，先记基线。这件事的设计已经写在每个 skill 的 eval/gate.json fix_list 里。只是没人跑。

第二，没有结构性质量的机械闸。A 档现在检测试、lint、类型、secrets、白名单、锁、新增依赖；不检圈复杂度增量、重复行、依赖方向。GitClear 和 arXiv 2608.25241 说这三项是 agent 代码退化最快的维度，OpenAI 的做法是把它们写成 linter。补法：done_when.yaml v2 的 constraints 加一节 structure（复杂度增量上限、重复率上限、允许的依赖方向），verify_structure.py 包一层现成工具（lizard、jscpd、dependency-cruiser），进 A 档。spec-gaming-detector 管作弊。这个管腐烂。两者不重叠。

第三，实现者拿不到"这个仓库怎么干活"。card_context.md 给卡、验收子集、红基线、约束，没给测试怎么跑、构建怎么起、模块地图在哪。sdlc 有意不做 rules/ 和 hooks，怕注入每个会话，结果这部分知识回到了每个人自己的 CLAUDE.md，正是差异的来源之一。OpenAI 的做法是 AGENTS.md 只做目录指向 docs/，arXiv 2606.20512 说指导文件该从失败里调出来。补法：/dos-extract 的 agent_guidelines 扩成一份仓库级 agent-map.md（跑测试、构建、目录职责、禁区），plan-cards 把与卡相关的切片塞进 card_context.md；/retro 从失败指纹里提"该加进 agent-map 的一句话"，这就是 probe-and-refine。

第四，模糊检测只有本体闭包一条客观触发。"哪个槽会改变产品形状"仍是引擎自评，而 Ambig-SWE 说模型判不准。/psl-derive 已经有一个好机制：同一份产品世界隔离推导 N 次，分歧集就是 G1 的议程。这个机制只给了 PSL 轨。补法：TASK 轨在 /issue 之后加一步，对同一 issue 隔离生成 2 到 3 份 done_when 草案，条目分歧处就是必须澄清的槽。成本是两三次短调用。换来一个不靠自评的模糊信号。

第五，流程不分大小。Böckeler 对 spec 工具的批评（一套流程不分任务大小、markdown 淹没 reviewer）对 sdlc 同样成立：三行 bug 修复也要经过 issue、契约、G2、卡、六审。sdlc 有单点使用入口和 PSL、TASK 双轨，但没有体量门。补法：intake 阶段加 size ∈ {S, M, L}，S 只走 issue、commit、pr-review 三步，M 免六审只跑 qa 与 gaming，L 全程；体量由改动文件数与 AC 条数推，写进 state.json，/retro 数逃逸缺陷时按体量分桶验证这个分法对不对。

还有两条我没排进前五但值得记：跨供应商评估（Codex 或 Gemini 审 Claude 的代码）在 spec-gaming-detector 里是"强烈建议"，没有接线，而这个环境里已经装了 codex 插件；review 的精确率（被 reviewer 推翻的 verdict 占比）已经在证据日志里，但 /tune 还没把它当输入。

## 补齐之后，完整的链路长什么样

把上面五条加进去，一个需求的路径变成：进来先定体量；模糊度由分歧集判而不是自评；实现者拿到卡加仓库地图切片；A 档多一道结构闸；每个版本的插件自己有一份带与不带对比的基线。人的差异在这五处各被压掉一部分：不会写需求的人被脚本拒回来补阈值，不会给上下文的人由卡和地图代劳，会作弊的实现（人或模型）被反向默认的审查抓，验收宽容的人由隔离评审替代，而"这套东西到底有没有用"不再靠信任。靠基线。

一个没想清楚的点：第一条缺口（行为对比）的评审 agent 如果还是 Claude，它对 sdlc 产出的偏好本身就可能是 sycophancy。基线跑之前，得先决定评审用哪家的模型。

### 第一轮运行的四个发现

行为层那一轮跑完，产出的不是排名，是四个 bug——两个在题目里，一个在 harness 自己的纪律上，一个在插件源码里：

| # | 发现 | 谁发现的 |
|---|---|---|
| E-01 | 隐藏集把「六列加在哪个函数上」的一种读法写死成唯一答案。`claudemd` arm 读了「别动已有接口」，合法地新加了一个函数，被判 0 分 | 收分时对比三个 arm 的产物 |
| E-02 | 欠定槽的证据模式比隐藏测试窄，同一件事一个说写了一个说没写 | 同上 |
| E-03 | **铁律「隐藏集只在收分时进场」只写在文档里，没有编译。** 收分早跑了一步，隐藏集落进还在干活的 arm 目录 | 那个 arm 自己报上来的 |
| E-04 | 结构层校验用的变量名覆盖了测试名清单，`tests_in_manifest` 报的是层数 | **被测的 arm 读插件源码发现的** |

E-03 的修法值得单独说：收分改成在**副本**里做，绝不碰 arm 的工作区；一次运行算不算污染由 mtime 机械判定
（泄漏晚于 arm 的全部产物 = 它没机会读到隐藏集），被判污染的结果不计入均值但留在报告里。
写在 README 里的纪律不是纪律——这正是整份报告在说的那件事，只不过这次犯的人是我。


### 行为层：十道题跑完（2026-09-06，30 次运行）

题库补到十道并全部跑完之后，**结论要泼冷水**：

| 维度 | bare | claudemd | aidlc |
|---|---|---|---|
| 全部十道 · 隐藏集 | 0.80 | 0.80 | 0.94 |
| 全部十道 · 欠定槽 | 0.55 | 0.60 | 0.95 |
| PSL 轨 · 只看不受混淆的 H1+H2 | 0.94 | 0.94 | 1.00 |

最后一行最该看。欠定槽与「不可判部分交给人」这两维，sdlc arm 的提示词**明确要求**它写台账，
所以那两维部分在测量它服从自己的指令。剥掉之后只留领域模型有没有被证伪：三个 arm 落在噪声带内。

**两条站得住的观察**：

1. **CLAUDE.md 在十道题上没有产生任何可测量的差别。** bare 与 claudemd 每个维度同分
   （TASK 轨 0.94/0.94、PSL 轨 0.66/0.66、H1+H2 都是 33/35），唯一的差是二十个欠定槽里多写了一个。
   这与报告正文引的 288 次运行一致，而 CLAUDE.md 正是业界默认做法。
2. **分开三个 arm 的是「写没写下来」，不是「做没做对」。** 这与报告的主张方向一致——
   变量一（信息补足）比变量二（上下文供给）更决定结果——但它证明的是"要求写台账就会写台账"，
   不是"这套纪律让人做得更好"。要分开这两者，得不给 sdlc arm 那段纪律、只给它脚本，再跑一轮。

**这一轮的另一半产出是五个题目 bug**（E-01/E-05/E-08 两处/E-09），全是同一个错：
出题人把自己的实现方式写进了判据——查用词、查函数名、查参数名、查架构位置。
规律写进了 `eval/effect/tasks/PSL-TRACK.md`：判据只能落在行为上或「有没有」上，不能落在「怎么做」上。

### 行为层：第一次有了读数（2026-09-06 第二轮，T01–T05 × 3 arm）

题库补到十道（五 TASK 五 PSL），跑了五道 × 三个 arm。**两个维度的结论不一样，所以分开判**：

| 维度 | bare | claudemd | aidlc | 判决 |
|---|---|---|---|---|
| 隐藏集：做对了没有 | 0.94 | 0.94 | 1.00 | 落在噪声带内（差 0.06，带宽 0.15） |
| 欠定槽：没说清的地方写下来了没有 | 0.50 | 0.60 | 1.00 | 超出噪声带（差 0.50） |

这个形状与报告正文引的 288 次运行一致：**上下文策略不移动正确率**。五道题三个 arm 几乎都做对了，
分开它们的不是「做没做对」，是「需求里没说清的地方有没有留下痕迹」——正是报告排第一的那个变量。

**这张表不能读成「sdlc 有效」的证明**，有三条硬伤，写在 `eval/effect/README.md` 里：
sdlc arm 被明确要求写台账，槽这一维部分在测量它服从自己的指令；出题人与被测者同源；n=5 是最低线不是可靠线。

PSL 轨那条「形态对不对没法用 pytest 判」的空白也有解了（`tasks/PSL-TRACK.md`）：不判形态，
判领域模型有没有被证伪（朴素模型在特定用例上给**相反**答案，这可以用 pytest），
以及不可判的部分有没有被**路由**给人（只判有没有路由，不判路由得对不对）。
